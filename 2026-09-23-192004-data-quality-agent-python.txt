  У попередньому проєкті є validate-dataset  skill, який потрібно пізніше

  Поки що лише коротко опиши, що саме ми будемо створювати.

⏺ Що ми створюємо

  Data Quality Agent — окремий Python-застосунок, що працює в терміналі.
  Перевірки даних виконує сам агент, а не Claude Code.

  Як він працює

  1. Запит у терміналі. Користувач пише звичайною мовою, наприклад: «перевір
     таблицю enrollments на дублікати й пропуски».
  2. Gemini як LLM. Модель розбирає запит і вирішує, які інструменти викликати.
     Для цього використовується function calling.
  3. Python-функції перевірок. Це набір інструментів, наприклад: профіль
     таблиці, частка NULL, дублікати ключів, діапазони значень, посилальна
     цілісність, формати дат і категорій. Логіку пізніше перенесемо з вашого
     skill validate-dataset.
  4. PostgreSQL. Агент підключається до бази через драйвер, наприклад psycopg.
     Параметри підключення беруться з .env.
  5. Захист SQL. Виконуються лише SELECT-запити. Для цього поєднаємо три речі:
     - сесію тільки для читання (read-only transaction);
     - перевірку запиту парсером, що пропускає лише один SELECT без DDL і DML;
     - statement_timeout і LIMIT.
  6. Markdown-звіт. Результат зберігається в reports/. Звіт розділяє три
     частини, як у validate-dataset:
     - підтверджені дефекти;
     - припущення;
     - питання до бізнесу.

  Орієнтовна структура

  - main.py — термінальний інтерфейс (CLI)
  - agent/ — цикл роботи з Gemini і реєстрація інструментів
  - db/ — підключення до бази та захист від небезпечного SQL
  - checks/ — функції перевірок, перенесені з validate-dataset
  - report/ — генерація Markdown-звіту
  - rules/ — правила якості для конкретних таблиць, якщо вони знадобляться
  - tests/ — тести, насамперед для захисту SQL і для перевірок

  Роль Claude Code

  - Пише код застосунку.
  - Через MCP course-db лише досліджує схему бази: які є таблиці, колонки та
    зв'язки. Це потрібно, щоб правильно спроєктувати перевірки. Якість даних
    Claude Code сам не оцінює.

  Коли будете готові, наступним кроком можу скласти детальний план реалізації, а
  потім перенести логіку з validate-dataset.

     Context

     Репозиторій зараз порожній: є тільки .claude/ і CLAUDE.md. Треба створити
     окремий термінальний застосунок на Python. Він приймає запит користувача,
     через Gemini (google-genai, function calling) обирає Python-тули перевірки
     якості, виконує в PostgreSQL лише безпечні SELECT і пише
     reports/data_quality_report.md. Логіка перевірок береться з попереднього
     проєкту:
     - ~/.claude/skills/synced/.../validate-dataset/SKILL.md — методологія:
       профілювання, 4 зрізи дублікатів, сентинели, діапазони, розділення
       «підтверджено / припущення / питання», ALL PASS;
     - .claude/skills/db-quality-check/SKILL.md — SQL-адаптація цієї методології
       для нашої БД;
     - lesson3_for_me/rules/enrollments_cleaning_rules.md — конкретні правила:
       progress_pct ∈ [0,100] (стаб 104), completed_at ≥ enrolled_at, формати
       дат.

     Шаблон інтеграції з Gemini беремо з сусіднього
     lesson4/simple-data-agent/agent.py: genai.Client, client.chats.create(...)
     з tools=[python_functions] і автоматичним function calling, модель
     gemini-2.5-flash. У lesson4/.venv уже встановлені google-genai 2.25 і
     python-dotenv.

     Схему вивчено через MCP (тільки information_schema, дані не читались).
     Числові колонки для перевірки діапазонів:
     - enrollments: progress_pct, last_week_reached, n_weeks, is_certified,
       course_no;
     - payments: amount_usd, is_refunded;
     - reviews: stars;
     - weekly_activity: week_number, minutes_watched, quiz_attempts, quiz_score;
     - dim_course: n_weeks, total_minutes, minutes_per_week, video_min,
       practice_min, mean_stars, pct_low, review_score.

     Дати в enrollments і reviews зберігаються як text.

     Кроки

     1. Каркас, залежності, секрети

     - Створити requirements.txt: google-genai, psycopg[binary]>=3.1,
       python-dotenv, PyYAML, pytest.
     - Створити .env.example із плейсхолдерами GEMINI_API_KEY=,
       GEMINI_MODEL=gemini-2.5-flash і
       DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DBNAME.
     - Змінити .gitignore: зараз .env.* ігнорує і .env.example, тому треба
       додати !.env.example. Ще додати .venv/, .pytest_cache/ і reports/*.md, бо
       звіти генеруються.
     - Створити dq_agent/config.py: load_dotenv(), а якщо змінних немає, помилка
       з назвою змінної. Значення в помилку не потрапляє. DATABASE_URL ніколи
       не друкується і не логується.

     2. Захист SQL — dq_agent/sql_guard.py

     - Перенести логіку з .claude/hooks/select_only.py:
       - normalise(): прибирає коментарі, рядкові літерали, dollar-quoting і
         quoted identifiers;
       - заборона ; усередині запиту (лише одна інструкція);
       - запит має починатися з ^(select|with)\b;
       - списки FORBIDDEN_KEYWORDS і FORBIDDEN_FUNCTIONS.
     - Замість sys.exit функція assert_safe_select(sql) -> None кидає
       UnsafeSQLError.
     - Хук .claude/hooks/select_only.py не змінюється, бо він захищає сам Claude
       Code.

     3. Підключення — dq_agent/db.py

     - psycopg.connect(DATABASE_URL, options="-c
       default_transaction_read_only=on -c statement_timeout=30000") і
       conn.read_only = True.
     - run_select(query, params) -> list[dict]: спершу assert_safe_select, потім
       виконання з row_factory=dict_row, fetchmany(MAX_ROWS) і rollback() у
       кінці.
     - Три рівні захисту: валідатор, read-only транзакція, таймаут і ліміт
       рядків.

     4. Whitelist ідентифікаторів — dq_agent/schema.py

     - Назви таблиць і колонок приходять від LLM, тож це ризик SQL-ін'єкції. Під
       час старту модуль один раз завантажує information_schema.columns для
       схеми public і кешує словник {table: {column: data_type}}.
     - Функції require_table(t), require_column(t, c) і numeric_columns(t).
       Невідома назва дає ValueError з переліком допустимих назв.
     - Уся динамічна SQL збирається через psycopg.sql.Identifier. Значення,
       наприклад межі діапазону, передаються тільки як параметри %s.

     5. Перенесення skill і правил

     - Створити docs/methodology.md: стислий переклад validate-dataset і
       db-quality-check:
       - межа між розділами 1, 2 і 3;
       - систематичність дефекту (GROUP BY за значенням порушення);
       - перекриття дефектів;
       - сентинели;
       - 4 зрізи дублікатів;
       - контракт приватності: лише агрегати, без ID, без вільного тексту, групи
         < 10 об'єднуються.

       agent.py вбудовує цей файл у system prompt.
     - Створити rules/ranges.yaml. Кожне правило має table, column, min, max і
       basis:
       - basis: rule для доведених правил → порушення піде в «Підтверджені»;
       - basis: assumption для евристик → порушення піде в «Припущення».

       Початковий набір:
       - progress_pct [0,100] (rule, lesson3 R3);
       - stars [1,5] (rule);
       - is_certified і is_refunded [0,1] (rule);
       - amount_usd ≥ 0; minutes_watched ≥ 0; quiz_attempts ≥ 0;
         last_week_reached ≥ 0 (rule);
       - n_weeks ≥ 1, week_number ≥ 1 (rule);
       - quiz_score [0,100] (assumption: шкала невідома);
       - mean_stars [1,5] і pct_low [0,1] (assumption: шкалу треба уточнити в
         бізнесу).
     - Створити rules/keys.yaml:
       - ID-колонки: enrollments.enrollment_id, users.user_id,

       - природні ключі: enrollments(user_id, course_id),

     - Створити dq_agent/rules.py: завантаження й валідація YAML. Якщо rules/

     6. Тули — dq_agent/tools.py

     Звичайні функції з type hints і docstring: Gemini читає їх як опис тулу.
     Кожна функція повертає dict лише з агрегатами і записує результат у
     results.py.

     Тул: describe_table(table)
     Що робить (SQL лише агрегатний): колонки, типи й nullability з
     information_schema.columns, PK/UNIQUE з table_constraints/key_column_usage,

     позначка «текстова колонка з датами» (за назвою *_at, *_date)
