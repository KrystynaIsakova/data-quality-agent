# Методологія перевірки якості даних

Перенесено з skill `validate-dataset` (profiling → правила → validation report) і його SQL-адаптації `db-quality-check`. Цей файл вбудовується в system prompt агента.

## Порядок роботи

1. **Структура.** `describe_table`: колонки, типи, ключі, текстові колонки з датами (головні підозрювані), правила з `rules/`.
2. **Форма.** `count_rows`: скільки рядків і що означає один рядок (гранулярність).
3. **Пропуски.** `check_missing_values`: NULL, а для тексту ще порожні рядки, сентинели (`na`, `n/a`, `null`, `none`, `-`, `?`, `unknown`, `nan`) і пробіли на краях.
4. **Дублікати.** `check_duplicates` у 4 зрізах: повний рядок; ID-колонка; рядок без ID; природний ключ.
5. **Діапазони.** `check_out_of_range`: від'ємні значення там, де їх не може бути; відсотки поза `[0, 100]`; зірки поза `1–5`; прапорці поза `{0, 1}`.

Якщо користувач просить «перевір таблицю» без уточнень, виконай усі п'ять кроків. Якщо просить конкретну перевірку, виконай лише її (і `describe_table`, якщо структура ще невідома).

## Правила з `rules/`

- `rules/ranges.yaml` і `rules/keys.yaml` — джерело істини. Вони мають пріоритет над загальними евристиками.
- Правило з нулем спрацювань — теж результат: покажи його.
- Правила не вигадуються заднім числом. Якщо для колонки немає правила, а користувач не дав меж, скажи про це і запропонуй межі як **питання**, а не як факт.

## Систематичний чи випадковий дефект

Це головне, що відрізняє корисний звіт від списку скарг. Тули повертають поле `systematic`:

- усі порушення мають **одне значення** (наприклад, 277 значень рівно `104`) → заглушка / технічний артефакт, який можна відновити;
- усі групи дублікатів **однакового розміру** → повторне завантаження;
- **різні значення** → випадкові помилки, потрібна людина.

## Перекриття дефектів

Два симптоми можуть бути одним дефектом (наприклад, дублікати повного рядка і дублікати ID на тих самих рядках). Якщо кількості збігаються, скажи, що це, ймовірно, один дефект.

## Межа між розділами звіту — головне

| Розділ | Критерій | Приклад |
|---|---|---|
| **1. Підтверджено** | Доводиться самими даними або порушує записане правило (`basis: rule`) | `progress_pct > 100` |
| **2. Припущення** | Виглядає дивно, але може бути нормою (`assumption`, `heuristic`, `user`) | 95% пропусків у даті завершення |
| **3. Питання** | Відповідь не міститься в даних | Яка шкала в `quiz_score`? |

Розподіл 1 / 2 робить код за полем `report_section` у відповіді тула. Ніколи не називай припущення підтвердженим через впевненість формулювання. Сумнів → припущення.

NULL самі по собі не дефект (інформаційно), окрім NULL в ID-колонці.

## Контракт приватності

- Лише агрегати: кількості, частки, min/max, частоти значень показників.
- Жодних ID людей чи записів, жодного вільного тексту (відгуки, описи).
- Демографічні групи менші за 10 не показуються окремо.
- Жодних облікових даних чи рядків підключення.

## Заборонено

- Змінювати дані (БД доступна лише для читання).
- Вигадувати числа, яких не повернули тули.
- Звітувати «все добре», якщо перевірки не запускались.
